# 独立运行架构（2026-10-18 定稿）

## 一句话

**NAS 不再是运行时，只是「配置分发 + UI 升级」的服务器。**
手机 / 电视的 App 自带前端与聚合能力，NAS 不在也能完整使用；PC 浏览器在 NAS 在线时用最新版。

## 角色分工

| 角色 | 职责 |
|---|---|
| NAS | 下发配置包（片源、直播源、UI 版本）、给 PC 提供网页版、可选做媒体代理 |
| 手机 App | 完整运行时：浏览 / 搜索 / 播放 / 投屏；配置来自上一次同步 |
| 电视 App | 完整运行时：接收投屏、自己也能浏览播放 |
| PC 浏览器 | 连 NAS 时使用最新版页面（无需安装） |

## 账户

**没有账户，没有 PIN。** 局域网自用，打开即用。
（服务端 `NO_AUTH=1` 为默认；想恢复多账户用 `NO_AUTH=0` 启动。）

## 数据流

```
        ┌──────────── 在线 ────────────┐
App ──► │ NAS /api/config/bundle        │──► 配置包（片源/直播/版本号）
        └───────────────────────────────┘
                    │ 存本地
                    ▼
        ┌──────────── 离线 ────────────┐
App ──► │ 本地聚合引擎（JS）            │──► 直接问源站（本地服务代发，绕开 CORS）
        └───────────────────────────────┘
```

关键点：**「离线」= NAS 不在，不是手机没网。** 手机有网（Wi-Fi 或蜂窝），
所以只要把「怎么问源站」的规则放到本地，就能自己查。

## 三个必须解决的坑

1. **CORS**：源站不会给 `127.0.0.1` 发 CORS 头。
   → 由 App 的本地服务代发请求（原生 HTTP，没有同源限制），页面只调 `/__fetch`。
2. **Referer/UA**：部分源校验来源。
   → 本地服务按配置里的 `referer` 规则补齐（已有基础）。
3. **解析规则**：NAS 上现在是 Python 适配器。
   → 收集站（cms）模式统一（`ac=list/detail` + JSON），用一份 JS 适配器覆盖；
   少数特殊源保留「仅在线可用」。

## 分阶段

| 阶段 | 内容 | 状态 |
|---|---|---|
| **S0** | 去掉账户/PIN，App 直接进 | ✅ 本次 |
| **S1** | NAS 提供 `/api/config/bundle`（片源+直播+版本），App 本地缓存 | 待做 |
| **S2** | 本地服务加 `/__fetch`（代发 JSON 请求，带 Referer/UA） | 待做 |
| **S3** | JS 端 cms 聚合：搜索 / 列表 / 详情离线可用 | 待做 |
| **S4** | 配置包的增量同步与版本提示（UI 升级走这里） | 待做 |
| **S5** | PC 端保持「连 NAS 用最新版」，不要装任何东西 | 已有 |

## 与旧架构的差别

| | 旧 | 新 |
|---|---|---|
| 页面来源 | NAS | App 内置（NAS 只在升级时推） |
| 内容聚合 | NAS | App 自己（S3 之后） |
| 账户 | PIN + 多用户 | 无 |
| NAS 挂掉 | 只能看缓存 | 完整可用（S3 之后） |
| 投屏 | 经 NAS 中转 | 局域网直连（已完成） |
